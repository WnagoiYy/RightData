# RightData 测试计划

更新日期：2026-10-23  
状态：测试方式与环境分工已确认；本文记录执行约定，不代表已完成部署或测试。

## 1. 默认测试方式

默认所有测试均在本机执行，包括服务端单元测试、接口测试、客户端功能测试及客户端与服务端联调。只有验证“外网客户端经内网客户端中转访问服务端”的跨网链路时，才按第 2 节部署远程环境。

| 组件 | 默认运行位置 | 用途 |
| --- | --- | --- |
| `server/` 服务端 | 本机 | 提供业务 API、测试数据库及文件服务 |
| `client/` Tauri 客户端 | 本机 | 验证界面、内网直连及业务流程 |
| 中转相关测试实例 | 本机，按用例需要启动 | 验证中转逻辑；本机模拟通过不能代替真实跨网验收 |

本机客户端通过可配置的后端地址连接本机服务端。普通业务测试不依赖远程部署或节点发现服务；涉及节点发现的专项测试使用第 3 节配置。多个客户端实例运行时，分别使用独立的身份、配置和运行数据，避免相互覆盖。

## 2. 外网经内网中转测试

### 2.1 环境分工

| 位置 | 部署内容 | 职责 |
| --- | --- | --- |
| `dacp` 对应的 SSH 主机 | `server/` 服务端、内网 Tauri 客户端及其所需中转组件 | 模拟内网环境；内网客户端连接服务端，并向外网客户端提供中转访问 |
| 本机 | 外网 Tauri 客户端 | 发现内网节点，通过该节点访问 `dacp` 上的服务端 |
| `discovery.example.com` | 节点发现服务 | 供客户端注册、发现节点；不作为业务后端地址 |

业务请求路径为：本机外网客户端 → `dacp` 内网客户端的中转组件 → `dacp` 服务端；响应沿原链路返回。节点发现服务不因承担发现职责而自动承担业务流量转发，底层连接方式按最终网络实现验证。

SSH 用于部署、启停和收集日志。跨网验收必须由本机客户端通过实际中转链路访问服务端，不能用 SSH 端口转发或直接请求后端代替。

`dacp` 表示用户指定的目标主机。部署前核实实际 SSH 别名、操作系统、架构及运行条件；历史资料曾使用 `dacp-internal`，不能仅凭历史名称认定当前连接配置。内网客户端必须具备运行 Tauri 和中转组件所需的环境，不能将“SSH 可连接”视为“客户端已正常运行”。

### 2.2 执行顺序与验收

1. 在本机完成本次变更相关测试，准备对应版本的服务端与客户端产物。
2. 通过 `deploy/` 中的脚本和配置，将服务端与内网客户端部署到 `dacp`。
3. 启动服务端，核验其就绪状态；配置内网客户端的后端地址，确认内网客户端可以正常访问服务端。
4. 配置两端的节点发现地址，确认内网节点注册、本机外网客户端发现节点及建立连接成功。
5. 从本机外网客户端执行登录、查询及本次变更涉及的业务操作；涉及文件或数据传输时，验证上传、下载、导入或导出的最终结果。
6. 结合两端客户端、中转组件及服务端日志，确认请求经过指定内网节点并到达服务端，记录实际链路与结果，避免误将直接访问后端判为中转成功。
7. 验证节点离线、发现服务不可达、后端不可达及断线重连时的状态反馈；写操作结果不明确时，先查询实际结果，不能盲目重复提交。

跨网测试通过的依据是节点发现、连接建立、中转请求、服务端处理及结果返回均得到验证；仅发现节点或建立连接不足以判定业务链路通过。

## 3. Tauri 客户端连接配置

节点发现服务器地址和 `server` 服务端后端地址均须可在 Tauri 程序中配置，无需修改源码或重新构建。

| 配置项 | 已确认约定 | 验证重点 |
| --- | --- | --- |
| 节点发现服务器地址 | 使用 `discovery.example.com`；允许在程序中修改 | 两端使用预期的发现服务；修改并重新连接后生效，重启程序后保留 |
| 服务端后端地址 | 可在程序中配置，按运行环境填写 | 本机直连指向本机服务端；`dacp` 内网客户端指向其可访问的服务端 |
| 连接方式与目标节点 | 区分内网直连与外网经中转访问 | 外网模式请求经过选定内网节点，不因设置后端地址而绕过中转 |

节点发现地址和后端地址分开保存、分开使用；协议、端口和必要路径在部署时按真实服务填写，不从 IP 地址推定。后端 API 统一使用 `/api` 前缀，客户端集中处理地址拼接，避免漏加或重复添加。

中转模式中的后端地址以实际发起后端请求的内网侧为准。例如，内网客户端使用回环地址时，它指向 `dacp` 自身，不能由本机外网客户端将其解释为本机服务端。具体配置入口和字段组织在客户端实现时细化。

配置验收包括地址校验、保存与重启保留、修改后重新连接，以及连接失败时区分发现服务、节点链路和后端故障。切换服务实例后重新校验登录身份。

## 4. 部署与测试文件归属

部署相关脚本、配置模板、服务定义和部署说明统一放入 `deploy/`，保持职责清晰。按实际需要创建子目录，优先复用已有位置，不提前创建空目录或占位文件。

| 建议位置 | 内容 |
| --- | --- |
| `deploy/scripts/` | 部署、更新、启停、状态检查及部署日志收集脚本 |
| `deploy/config/` | 本机、`dacp` 与节点发现服务所需的部署配置模板，明确环境和组件归属 |
| `deploy/docs/` | 部署步骤、配置项、运行条件及恢复说明 |
| `deploy/artifacts/` | 部署用安装包和服务端产物，按环境及版本区分，按需生成并忽略 |
| `deploy/runtime/` | 部署过程临时文件和日志，按需生成并忽略 |
| `test/` | 测试代码、用例、测试数据及测试配置；跨端集成测试也放在此目录 |
| `test/results/` | 测试报告及验收日志，按测试批次保存 |

部署脚本以配置参数指定 SSH 主机、远程安装位置和服务地址，避免散落硬编码；配置模板不包含真实密码或令牌。已有源码目录中的部署模板如需用于本方案，实施时统一整理到 `deploy/`，避免维护重复副本。

生成文件和忽略规则均放在项目允许的四个目录内。测试结束后清理本次产生且不再需要的临时内容，保留必要验收记录，不删除已有用户数据。

## 5. 结果记录与关联计划

每次测试记录测试模式、本机与远程组件版本、实际 SSH 目标、连接地址、目标节点、关键用例结果及相关日志位置。地址记录不包含认证凭据；未执行、失败和通过分别标明，历史实验结果不作为当前版本的通过结论。
